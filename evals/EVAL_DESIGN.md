# Evals 설계서

작성일: 2026-11-08. 현재 MVP의 평가 대상, 데이터셋, 채점 방법과 합격선을 정의한다. 기존 골든 케이스와 테스트는 변경하지 않는다. 실행·검토 상태는 6절에 정리한다.

## 1. 평가 대상과 지표

**사용자 결정(2026-11-08):** 1단계는 현재 규칙 기반 MVP(`stub`)를 평가하고, 실제 AI 평가는 별도의 후속 단계로 관리한다. 평가 범위 선택 후 현재 stub의 사례별 기대값 20건은 사용자 확인을 반영했다. 합격선도 사용자 확인을 반영했다. 실제 모델의 실행·수집은 후속 단계다.

- `stub`: 현재 `web/js/ai-stub.js`의 실제 `aiSuggest(query)`를 Node 어댑터로 실행. 외부 호출 없이 행동 한 줄과 출처를 평가한다. `{action_text: action}` 변환은 검사 어댑터 표현이며 제품에 네 필드 추출을 구현했다는 뜻이 아니다.
- `stored_model`: 사람이 별도 수집한 최초 모델 원출력 JSONL을 읽고 기존 schema·policy와 사람이 확정한 기대 조건을 검사한다. API·모델 호출·형식 복구 실행은 구현하지 않는다. 기존 개발용 파서 러너의 8건 실행을 새 20건 평가로 재분류하지 않는다.
- 대상별 기대값과 이력은 분리한다. stub에만 있는 source 검사와 모델 네 필드 검사의 점수를 직접 비교하지 않는다. 현재 선택 대상은 `review_decisions.json`의 stub이다. 후속 stored_model 전환은 별도 기대값·수집 버전·검토를 거친다.
- AC4 저장·확인, AC5 과업 분리, AC6 전체 맥락 표시, AC7 전체 재시도·외부 작업 실행 금지는 이 러너의 평가 범위가 아니다. 기존 골든/브라우저 검사와 사용자 관찰을 별도로 유지한다.

| 지표 | 연결 AC | 분자 / 분모 | 채점기 | 합격선 |
|---|---|---|---|---|
| overall | AC1·AC2·AC3의 출력 범위 | 모든 공통·기대 조건 충족 건수 / 전체 입력 수 | 기존 schema·policy + code | 사용자 확인: 1.0 (20/20) |
| clarification | AC2 | 사람이 재질문 대상으로 정한 사례 중 전체 조건 충족 / 해당 사례 수 | code | 사용자 확인: 1.0 (10/10) |
| critical | AC1·AC2·AC3의 지정 절대 규칙 | 스키마/원문 위반, 금지 필드·금지값 출력, 재질문 입력의 행동 생성, 출처 훼손이 있는 사례 수 / 전체 입력 수 | code | 사용자 확인: 0건; 평균 점수로 상쇄 불가 |
| errors | NF5 | 응답 누락·전송/파싱/채점 오류가 있는 사례 수 / 전체 입력 수 | code | 사용자 확인: 0건. 해당 사례는 overall에서 실패하므로 20/20 조건으로 함께 요구 |
| categories | 동일 AC | 범주별 통과 / 범주별 전체 | code | 진단용. 범주별 합격선을 승인한 것으로 해석하지 않음 |

지정 critical은 사례 단위로 한 번만 센다. 이유는 건별 checks/errors에 모두 남긴다. wrong action을 모두 critical로 추론하지 않으므로, 중대 오류에 해당하는 원문 값은 사람이 `forbidden_values`에 구체적으로 지정해야 한다. 미판정·오류를 분모에서 빼지 않는다. 최초 실패 후 복구·사용자 수정으로 성공을 바꾸지 않는다. grade 조건을 통과해도 전체 제품 AC 충족이나 스파이크 채택을 뜻하지 않는다.

## 2. 데이터와 사람의 기대 조건

`evalset.jsonl`에는 합성 입력 20건이 있다. normal 4, conflict 4, clarify 3, out_of_scope 3, injection 3, hallucination 3. 2026-11-08 사용자가 추천 정답 20건과 세 가지 보완사항의 반영을 요청하여 현재 stub 기대값 20건을 모두 반영했다(행동 후보 10건·후보 없음 10건). [사례별 정답과 근거](CASE_REVIEW.md)를 함께 본다. 모델 기대값 20건은 null이다. 현재 MVP의 사례별 기대값과 합격선은 사용자 확인을 반영했다.

입력 문자열은 기존 골든·semantic_cases·프롬프트 예시를 복사하지 않았다. 이미 논의한 오류 유형은 포함하므로 '처음 보는 유형'이라고 주장하지 않는다. 현재 제품에 실행하지 않았으며 실제 평가 적합성과 미사용 여부는 사람이 확인한다. 검토 전 제품 출력으로 기대값을 맞추지 않는다.

스파이크와 자료를 공유하려면 새 20건·모델 기대값을 팀원 두 명이 서로의 답과 모델 출력을 보지 않고 작성한 뒤 합의한다. 실제 라벨 작성자는 기록하되 AI가 대신 이름·일시를 만들지 않는다. 팀이 이미 자료를 개발에 사용했다면 `dataset_role=development`로 표시하거나 새 자료를 준비한다. 출력·오류를 보고 제품을 수정한 뒤 같은 자료로 실행한 결과는 회귀/개발 결과이며 새로운 독립 holdout 근거가 아니다.

각 행은 `id/category/query/expect/graders/note`를 사용한다. expect는 `stub`·`stored_model`로 분리하고 선택한 대상만 사람이 채워도 된다. 다음은 **기대값 작성 형식**이며 실제 라벨이 아니다.

```json
{
  "outcome": "candidate 또는 clarification 중 사람이 선택",
  "allowed_actions": [],
  "required_fields": {},
  "forbidden_fields": [],
  "forbidden_values": {}
}
```

- candidate: `allowed_actions`에 허용하는 행동 원문 구절을 한 개 이상 작성. 유효한 표현이 여럿이면 각각 기입한다. 정답 한 문장으로 생성 문구를 강제하는 대신 허용 원문 조건을 검사한다.
- clarification: `allowed_actions=[]`, `required_fields={}`. action_text=null이며 다른 속성을 붙이지 않아야 한다.
- required_fields: 선택 속성 이름 → 허용 원문 구절 목록. 모델의 상태·장애·기한 귀속을 사람이 결정한다. stub은 이 세 필드를 추출하지 않으므로 모델 기준을 자동 복사하지 않는다.
- forbidden_fields: 출력하면 안 되는 선택 속성 목록. 미기록·없는 정보를 사람이 구분한다.
- forbidden_values: 속성 이름 → 중대 오류로 지정하는 문자열 목록. 잘못 귀속한 상태·기한 등을 사람이 직접 기입한다.
- code 이외의 graders, 미지원 키, 빈 기대 조건, 중복 ID·행동/기대 조건 모순을 거부한다. 미구현 judge를 켜서 채점을 생략하지 않는다.

### 출력 평가와 별도 검사의 경계 — 사용자 확인 반영

- 03·04: 행동 후보 정확도와 상태·기한 원문 보존을 구분한다. source가 원문 구절이라는 검사만으로 상태·기한 전체 보존을 선언하지 않는다. 저장·재표시는 별도 브라우저 검사 대상이다.
- 12~14: 이번 정답은 후보 없음뿐이다. 재질문 안내 문구와 실제 외부 작업 실행 금지는 별도 UI·통합 검사에서 검증한다.
- 15·17: 해당 지시문이 실제 작업 후보에 섞이지 않았는지만 평가한다. 일반적인 인젝션 방어 완료를 뜻하지 않는다.

### 현재 MVP 합격선

| 항목 | 사용자 확인 기준 | 이유 |
|---|---|---|
| overall_min | 1.0 — 20/20 | 범위가 제한된 결정적 MVP의 고정 20건이다. 이미 확인한 기대 조건의 실패를 남긴 채 회귀 수용하지 않는 안이다. 모집단·실제 모델 정확도 100%를 요구하는 뜻은 아니다. |
| clarification_min | 1.0 — 10/10 | 불명확·미선택·미채택·취소·대신 실행 요청에 임의의 후보를 만들지 않아야 한다. |
| critical_max | 0건 | 스키마·원문 위반, 후보 없음 기대 사례의 행동 생성, 출처 훼손 등 지정 절대 규칙은 평균 점수로 상쇄하지 않는다. |
| errors | 0건 | 누락·파싱·채점 오류도 실패로 분모에 남긴다. overall=20/20이면 오류 0건이 함께 필요하며 별도 errors_max 게이트 구현은 아니다. |

2026-11-08 사용자가 이 기준의 문서 반영을 요청했다. 현재 MVP를 위한 사용자 확인 기준이며 교수님이 지정한 수치나 실제 모델 스파이크 18/20의 전용이 아니다. review_decisions.json의 thresholds에 1.0·1.0·0을 반영하고 threshold_decision에 결정 이유와 범위를 기록했다. 실행 준비 상태는 6절과 review_decisions.json을 따른다. 최초 베이스라인은 합격선 미달이어도 결과를 그대로 남기며 정답·합격선을 점수에 맞춰 낮추지 않는다. 특정 사례 실패를 분석한 뒤 같은 자료로 수정·재실행하면 개발/회귀 결과로 표시한다.

## 3. Judge와 사람 검토

이번 출력은 제한된 원문 추출이므로 합의한 원문 구절과 금지 조건을 코드로 검사하는 안을 준비했다. LLM judge는 사용하지 않고 비용·호출은 0이다. 의미상 유효한 허용 구절·귀속을 정하는 판단은 여전히 사람의 일이다. 사람이 지정하지 않은 의미를 코드가 자동 판정한다고 주장하지 않는다.

팀이 judge가 필요하다고 결정하면 judge_prompt·기준별 이유/pass 출력·모델·버전을 먼저 설계하고, judge 출력을 보기 전에 작성한 사람 라벨과 지침의 일치율 검증을 거쳐야 한다. 현재 러너는 judge가 지정되면 거부한다. `judge_prompt.md`에 미사용 사유를 남겼으며 사람 라벨/일치율을 꾸미지 않는다.

## 4. 실행 절차와 승인 기록

1. `python3 evals/run_evals.py --check --target stub`로 입력 구조·미확정 항목·현재 해시를 확인한다. **제품 실행·점수·결과 파일은 만들지 않는다.** 정상 종료는 준비 완료를 뜻하지 않으며 ready=false의 사유를 읽는다.
2. 팀이 평가 대상, 사례·비율·기대값, 세 지표의 합격선과 근거, 데이터 역할을 결정한다. golden_review_reference는 현재 진행 중인 골든 검토가 실제 끝난 후 그 기록을 연결한다.
3. 러너 결함 주입을 사람이 검토하고 runner_review_reference를 작성한다. 현재 기계 self-test 결과는 사람 승인과 다르다. 승인 후 판정 로직 변경은 재검토 대상이다.
4. 모든 입력·기대값·문서가 확정된 **마지막에** --check가 표시하는 해시를 review_decisions.json의 frozen_hashes에 기록한다. 실제 검토자·승인일시·근거를 입력하고 status=approved로 바꾼다. 도구가 사용자를 대신해 채우지 않는다.
5. `python3 evals/run_evals.py --run --target stub --change "실제 변경 설명"`으로 최초 실행한다. draft·null·해시 불일치면 결과 생성 전에 중단한다. 제품 소스는 수정하지 않는다.
6. 실행마다 결과 JSON·history.csv·오류 분석 초안이 생긴다. 출력은 코드 채점기로 전수 검사하며 분자·분모와 사례별 검사를 출력한다. --change는 실제 변경 사실만 적는다.

stored_model은 동일 승인 절차 후 `--run --target stored_model --outputs <최초출력.jsonl> --change ...`로 실행한다. 각 행은 `id/raw/status/attempt_index/query_sha256`를 갖고 attempt_index는 0이어야 한다. raw는 실제 최초 모델 JSON 텍스트, status는 정상 종료일 때 stop이다. query_sha256은 해당 입력의 UTF-8 SHA256이다. 누락·실패·입력 해시 불일치는 실패로 분모에 남긴다. 중복·알 수 없는 ID는 잘못된 실행 자료로 실행 전 거부한다.

model_metadata에는 실제 model, prompt_hash, schema_hash, collection_run_id를 적는다. schema_hash는 현재 스키마 파일과 일치해야 한다. 이 러너는 별도 수집 절차가 실제 동결 프롬프트·예산을 지켰는지 자동 보증하지 않는다. 수집 원본은 최초/복구를 분리하고 호출 수·시간·사용량을 별도로 보존한다. 모델 수집 도구와 실제 호출은 이번 준비 범위에 포함하지 않았고 실행하지 않았다.

## 5. 결과 저장·베이스라인·비교

- 실행 ID는 UTC 마이크로초 시각+난수. 결과 파일은 배타적 생성으로 덮어쓰지 않는다. 동시에 실행하면 .evals.lock으로 차단한다. 비정상 강제종료 후에는 실행 여부 확인 없이 잠금을 지우지 않는다.
- commit과 dirty 상태, 실제 dataset/design/grader/adapter/schema/policy/product/decision 해시, 선택 대상, 승인 자료, 최초 출력과 각 검사·오류를 보관한다. 명령의 golden 결과 문자열을 사실 검증 없이 통과 증거로 받지 않는다.
- 결과의 golden_status는 별도 골든 검토 기록을 참조한다. Evals 실행 결과와 제품 전체 완료 판정은 구분한다.
- 합성 평가 입력·출력만 기록한다. 실제 인터뷰 원문·비공개 링크·키는 이 평가셋에 넣지 않는다. 실제 모델의 미측정 지연·비용은 추정하지 않는다.
- 첫 실행 점수가 낮아도 그대로 저장한다. 보고 전 점수에 맞춰 기대값·합격선을 바꾸지 않는다.
- 비교는 같은 target·dataset·grader·adapter·schema·policy·design·판정 기준·데이터 역할끼리 한다. 제품 버전이 바뀌면 해시로 식별한다. 대상이 다른 두 실행은 직접 비교하지 않는다. 현재 stub은 결정적이나 실제 모델은 같은 설정 3회 변동을 확인하고 비교 허용 오차를 사람이 정해야 한다. 이 러너는 개선/회귀를 자동 선언하지 않는다.
- 실패 최대 10건을 실제 건수만큼 펼쳐 checks/errors를 적고 범주별 실패 수를 집계한다. 원인·개선 백로그는 사람이 작성한다. 실패가 0개면 만들어 내지 않는다. 오류 원인별 건수와 범주별 실패 수를 혼동하지 않는다.

## 6. 실행 준비 상태

현재 팀 검토 중이다. 사례 20건과 합격선은 사용자 확인을 반영했으며, 공식 평가는 아직 실행하지 않았다. 상세 상태는 review_decisions.json에 기록한다.

- 평가 대상은 사용자 결정으로 stub 우선·실제 모델 후속 단계로 정했다. 모델 실행·수집 승인은 아직 없다.
- 현재 stub의 20건 행동 기대값은 반영 완료. 후속 모델의 선택 필드·절대 규칙 기대값은 별도로 결정한다.
- 현재 MVP 합격선은 사용자 확인으로 overall 20/20·clarification 10/10·critical 0건·오류 0건을 반영했다. 러너 수용 기록·자료 역할 확인은 남아 있다. 실제 모델 합격선으로 자동 전용하지 않는다.
- 독립 라벨·합의 담당자와 실제 완료 일시, 미사용 평가 자료인지 또는 개발 자료인지.
- 골든 검토 결과 연결과 러너 결함 주입·수용 기록.
- judge 필요 여부(현 안은 미사용), 모델을 쓸 때 수집 버전·예산·실행 요청.

현재는 Evals 실행 도구 준비와 기계 self-test 단계다. 20건의 제품 실행·공식 베이스라인·사용자 효과 측정·사람 승인·강의07 제출 완료는 주장하지 않는다.
