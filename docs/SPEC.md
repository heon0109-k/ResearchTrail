
## 1. 문제

**프로젝트나 스터디 발표를 위해 낯선 AI 문헌을 읽는 컴퓨터공학 학부생 중에는 중단한 과업으로 돌아왔을 때 흩어진 기록에서 자료를 남긴 이유·마지막 판단 또는 미해결 질문·다음 작업을 함께 되찾지 못해 이전 대화와 메모를 되짚느라 실제 검토·작성에 착수하는 시간이 늦어지는 사람이 있다.**

근거는 로그 4 [P04-Q03][I04-03]·[Q10][I04-10]·[Q11][I04-11]과 로그 6 [P06-Q03][I06-03]·[Q10][I06-10]이다. 문제의 반례, 시간값의 해석, 대상 범위 조정과 반증 조건은 [PROBLEM.md](PROBLEM.md#evidence)에 둔다.

이번 제품은 **이미 기록한 맥락을 되찾아 다음 행동으로 이어 가는 것**을 돕는다. 기록 위치를 찾았다고 수식 이해, 과학적 판단, 실험 실행까지 해결되었다고 주장하지 않는다.

<a id="users"></a>
## 2. 타깃 사용자

1차 대상은 최근 4주 안에 AI 프로젝트 또는 스터디 발표를 위해 논문 두 편 이상을 직접 읽거나 검토하고 과업을 중단했다가 재개한 경험이 있는 컴퓨터공학 학부생이다. 기존 방식으로 수월하게 재개한 사람도 비교 대상에 포함한다.

이는 “출발 방향 선정”을 중심에 둔 기존 문서에서 “프로젝트·발표 준비의 재개”까지 함께 검토하자는 **범위 조정 제안**이다. [PROBLEM.md 2절](PROBLEM.md#target-users)의 결정과 항상 일치시킨다. P04·P05·P06의 과업 차이를 없애거나, 인접 대학원생을 학부생 표본에 더하지 않는다.

현재 비대상은 자동 논문 우열 판정, 완전한 학습 지도, 연구·메일·알림의 대행 실행, 비공개 조직 자료의 외부 처리, 전체 외부 도구 동기화를 주요 목적으로 삼는 사용자다. 기존 노트가 충분한 사용자에게 도구 이전을 강요하지 않는다.

<a id="core-flow"></a>
## 3. 핵심 기능

**문헌 과업 선택 → 짧은 기록과 필요한 맥락·자료 위치 남기기 → 다음 작업 한 건의 후보 추출 → 사용자 검토·확인 → 같은 과업을 다시 열 때 저장된 맥락과 확인한 작업을 함께 보여 주기.**

### 3.1 기본 사용 흐름

| 단계 | 사용자의 행동 | 시스템의 책임 |
|---|---|---|
| 1. 과업 선택 | 기존 `ResearchTask`를 선택하거나 목표를 적어 새 과업을 만든다. | 과업의 존재와 현재 작업공간의 접근 권한을 확인한다. |
| 2. 기록 | 짧은 메모를 남긴다. 필요할 때만 질문·판단·문헌 사용 이유·자료 위치를 보완한다. | 원문 메모를 `ResearchRecord`로 보존한다. 선택 항목이 없다는 이유로 메모 저장을 막지 않는다. |
| 3. 작업 후보 추출 | 그 메모를 바탕으로 다음 작업 후보를 요청한다. | 해당 메모 한 건만 파싱한다. 저장소 전체·과거 대화·문헌 본문을 자동 수집하지 않는다. |
| 4. 검토·확인 | 원문과 후보를 비교하고 필요하면 수정한 뒤 저장을 확인한다. | 확인 전 후보를 확정된 `NextAction`으로 저장하지 않는다. 행동과 과업 연결을 다시 검사한다. |
| 5. 재개 | 같은 과업을 다시 연다. | 해당 과업에 실제로 저장된 기록·맥락·확인된 작업만 보여 준다. 없는 목적·판단·위치를 생성하지 않는다. |

**핵심 구분:** 메모를 저장하는 것과 다음 작업을 확정하는 것은 다른 동작이다. 파싱이 실패해도 원문 메모는 남길 수 있어야 한다. 사용자가 작업 후보를 취소하면 메모만 남고 확정된 작업은 생기지 않는다.

### 3.2 AI와 사용자·애플리케이션의 역할

| 구분 | 이번 버전의 담당 |
|---|---|
| AI | 메모에 실제로 표현된 다음 행동, 그 행동의 진행 상태·장애·기한을 추출한다. |
| 사용자 | 과업을 선택하고, 목적·질문·실제 판단과 자료 연결을 입력·선택하며, 후보를 검토해 확정한다. |
| 애플리케이션 | 입력·출력 검증, 재질문, 호출 제한, ID·권한 확인, 저장, 과업별 조회를 수행한다. |

목적·질문·판단은 메모 전체에서 자동 추출하지 않는다. 현재 `NextAction` 파서에 다른 도메인 클래스의 필드를 추가하지 않는다. **재개 화면도 첫 버전에서는 저장 내용을 조회·배치하는 화면이며, 새 요약이나 연구 계획을 생성하는 LLM 기능이 아니다.**

### 3.3 정상·예외 시나리오

정상 흐름은 “논문 A의 표 2 확인”처럼 행동이 구체적인 메모를 남기고, 후보의 상태와 기한을 확인한 뒤 저장하고, 다음 방문에서 해당 작업과 관련 기록을 다시 여는 경우다.

“지난번 하던 거 이어갈래”처럼 행동을 특정할 수 없으면 메모는 유지하되 작업을 확정하지 않는다. 시스템은 어떤 행동을 기록할지 묻는다. 다음 행동을 아직 정하지 못한 사용자도 질문이나 현재 상태만 남길 수 있으며, 빈칸을 없애려고 가짜 `Decision`이나 `NextAction`을 만들지 않는다.

이 시나리오는 제품 설계 설명이다. 실제 제품 사용 결과로 제시하지 않는다.

### 4.2 비포함 범위

|---|---|

| PDF·손글씨·수식의 자동 추출, 자동 정밀 위치 이동 | 사용자가 남긴 위치 단서를 보존한다. 본문 다운로드·OCR·구절 검증은 수행하지 않는다. |

| 모델 학습, 코드 실행, 메일 전송, 알림 예약 | 메모의 행동을 대신 실행하지 않는다. |
| 미확인 자료 접근 제한의 자동 해결 | 미확보·접근 실패를 정보로 남길 수 있으나 확보를 보장하지 않는다. |
| 외부 조직 자료의 무승인 전송, 기업·병원 정책의 임의 판정 | 공개 가능한 자료와 사용자가 전송에 동의한 메모로 초기 사용 범위를 제한한다. |
| 전역 지식 그래프, 전 관계의 자동 추론 | 온톨로지는 개념의 정본이다. 그래프 데이터베이스나 모든 관계 구현을 요구하지 않는다. |
| 일반적인 협업·권한 관리 플랫폼 | 개인 작업공간의 분리와 접근 확인을 우선한다. 조직 단위 협업 기능은 별도 명세가 필요하다. |

앞의 외부 동기화·과학적 판단·학습 보장·실행·자료 확보·비공개 처리 제외는 `ontology.yaml → scope.out_of_scope`를 유지한 것이다. RAG, OCR, 자동 수집, 조직 협업의 후순위화는 이 첫 버전의 **추가 범위 축소 제안**이다. 온톨로지에서 개념을 삭제한 것으로 해석하지 않는다.

### 4.3 데이터 경계와 공통 규칙

도메인 클래스와 속성 이름은 `ontology.yaml`을 따른다. 모든 클래스를 하나의 LLM 출력에 평탄화하지 않는다. 다음 표는 이번 흐름에서 사용하는 부분만 정리한 것이다.

| 개념 | 이번 버전에서 다루는 내용 | 생성·확인 주체 |
|---|---|---|
| `ResearchTask` | `goal_text`, 선택적인 `scope_text`, `target_output_text`, `progress_text` | 사용자 입력 |
| `ResearchRecord` | 원문 `content_text`, 필요할 때 기록 종류·작성 주체·위치·검토 상태 등 기존 속성 | 사용자 입력, 원문은 그대로 보존 |
| `ResearchQuestion` | `question_text`, 알려진 `state_text`, `unresolved_reason_text` | 사용자가 질문을 별도로 남긴 경우만 |
| `Decision` | `decision_text`, 알려진 `made_by_text`, `reason_text` | 실제 판단을 사용자가 입력한 경우만 |
| `DocumentUse` | `purpose_text`, `role_text` 등 과업별 사용 맥락 | 사용자가 특정 문헌과의 연결을 지정한 경우만 |
| `Document` / `DocumentArtifact` / `EvidenceExcerpt` | 문헌 정체성, 파일·판본·접근 단서, 특정 대목의 위치·확보한 구절을 구분해 보존 | 사용자 입력·선택. 본문을 가져오거나 내용을 검증하지 않음 |
| `NextAction` | 기존 스키마의 네 속성과 사용자 확인 후의 과업·기록 연결 | AI 후보 또는 수동 입력을 사용자 확인 후 확정 |
| `ResumeEpisode` | 향후 재개 관찰에서 개별 사건을 구분하는 개념 | 이번 구현에 자동 추적·타이머·별도 입력 화면을 추가하지 않음 |

`task_id`, `record_id`, `next_action_id`, 작업공간 식별자, 저장 시각과 처리 상태는 애플리케이션의 기술 필드다. 이를 인터뷰가 직접 요구한 도메인 속성이나 모델이 추출할 값으로 추가하지 않는다.

공통 규칙은 다음과 같다.

- **없는 정보는 만들지 않는다.** 실제 판단이 없으면 `Decision`을 생성하지 않는다. 관계가 기록되지 않은 것과 실제 관계가 없다는 것을 구별한다.
- **상태를 합치지 않는다.** 자료 확보, 읽음, 질문 해결, 원문 대조, 채택, 행동 착수·완료는 서로 다른 값이다. `state_text`·`progress_text` 등에 새 enum을 강제하지 않는다.
- **확인은 진실 보증이 아니다.** 사용자가 저장을 확인한 것은 기록 내용과 연결에 대한 확인이며, 논문 내용의 과학적 정확성을 보증하지 않는다.
- **원문과 수정 내용을 구분한다.** 입력 메모와 원래 모델 후보를 변경하지 않고, 사용자가 수정한 최종 값은 별도로 보존한다. 수정된 사용자 문장은 원문에서 추출된 구절이라고 표시하지 않는다.
- **최신 저장과 최신 판단을 구별한다.** 기본 정렬은 저장 시각 내림차순, 동률은 ID 오름차순이다. 늦게 저장한 옛 회의 메모를 최신 판단이라고 자동 승격하지 않는다.

근거: `ontology.yaml → modeling_conventions`, `domain_constraints.D01–D10`, `classes.ResearchRecord`, `classes.Decision`, `classes.NextAction`.

### 4.4 비기능 요구사항 — 구현 목표, 아직 검증되지 않음

| ID | 요구사항 | 검증 방법 |
|---|---|---|
| NF1 | 메모 한 건의 모델 호출은 최초 호출과 형식 복구 한 번을 합해 최대 두 번으로 제한한다. 호출별 제한 20초, 두 시도를 포함한 네트워크 처리 제한 40초를 제품 초깃값으로 제안한다. | 가짜 시계·응답을 사용한 횟수·시간 경계 테스트. 제한 후 늦게 온 결과가 자동 저장되지 않는지도 검사한다. |
| NF2 | 저장·재열람은 모델 사용 가능 여부와 분리한다. 재개 조회는 모델과 외부 자료 사이트를 호출하지 않는다. | 모델 어댑터를 사용할 수 없게 한 상태에서 저장·조회 검증, 외부 호출 수 0 확인 |
| NF3 | 전송 전 사용자가 메모의 외부 처리 여부를 확인할 수 있어야 한다. 미동의 시 외부 모델 호출 없이 수동 기록을 제공한다. 비밀키·원문 메모·비공개 링크를 공개 운영 로그에 남기지 않는다. | 전송 함수 감시, 키 표식 문자열 검사, 동의 거절 경로 테스트 |
| NF4 | 메모만 먼저 저장할 수 있고, 목적·판단·질문·자료 연결은 선택 사항이어야 한다. 입력·후보 수정·확인·취소·재열람을 키보드로 수행할 수 있고 상태를 색상만으로 표현하지 않는다. | 최소 입력 E2E 테스트, 키보드 점검표, 상태·오류 문구 확인 |
| NF5 | 모델 결과의 JSON·스키마·정책 검사와 사람의 의미 판정을 분리하고, 모델·프롬프트·스키마 버전 및 최초/복구 응답을 구분한다. 측정하지 않은 사용량·지연·비용은 미측정으로 기록한다. | 실험 결과 파일과 메타데이터 검사, 누락 값 처리 테스트 |
| NF6 | 접근할 수 없는 과업·기록을 읽거나 연결하지 않는다. 외부 링크는 자동 수집하지 않으며, URL 클릭을 지원할 경우 허용한 안전한 형식만 연다. | 다른 작업공간의 ID, 없는 ID, 실행형 링크 문자열을 포함한 경계 테스트 |

NF1의 제품 제한값은 설계 권고이며 실측 성능이 아니다. 현재 실험 러너의 **전체 실험 180초, 최대 16회 호출, 생성 토큰 상한**과 구별한다. 로컬 시간 초과가 공급자의 이미 접수된 요청 중단을 보장한다는 의미도 아니다.

초기 제품의 응답속도·동시 사용자 수·정확도는 아직 측정되지 않았다. 근거 없는 “몇 초 이내 항상 성공”이나 정확도 수치를 성능 실적으로 기재하지 않는다. 실제 사용자 배포 전에 측정 환경과 부하 조건을 명시한 성능 목표를 추가 검토한다.

## 5. 인터페이스

### 5.1 인터페이스의 역할

다음 HTTP 경로는 **첫 구현을 위한 제안**이다. 프레임워크·DB·배포 방식은 이 문서에서 새로 확정하지 않는다. 서버에서 적용할 작업공간 식별과 접근 확인은 모든 저장·조회에 공통으로 적용한다.

| 인터페이스 | 입력 | 출력 | 부수효과 |
|---|---|---|---|
| `POST /tasks` | `goal_text`, 선택적인 `scope_text`, `target_output_text`, `progress_text` | `{task_id, task}` | 과업 생성 |
| `GET /tasks` | 현재 접근 가능한 작업공간 | `{tasks: [{task_id, task}]}` | 없음 |
| `POST /tasks/{task_id}/records` | `{record, context?, revises_record_id?}` — 5.2절 | `{record_id, context_refs}` | 원문 기록과 사용자가 명시한 맥락 저장 |
| `POST /tasks/{task_id}/records/{record_id}/parse-next-action` | `{external_processing_confirmed: true}` | `{candidate, next_action, attempt_count}` — 5.3절 | 모델 호출 가능. 확정된 작업 저장은 없음 |
| `POST /tasks/{task_id}/next-actions` | `{source_record_id, reviewed_action, confirmed, links?}` — 5.4절 | `{next_action_id, source_record_id, saved_action}` | 사용자가 확인한 작업 저장 |
| `GET /tasks/{task_id}/resume` | 과업 ID | `{task_id, task, records, context, next_actions}` — 5.5절 | 없음. LLM 호출 없음 |

`task`와 각 도메인 객체의 내용은 온톨로지의 해당 속성을 따른다. 사람 입력에서 미상인 선택 속성은 생략하거나 `null`로 줄 수 있고, 조회 시 미상 값은 `null`, 등록된 항목이 없는 목록은 `[]`로 표현한다. 내용이 필수인 객체는 그 내용을 입력했을 때만 생성한다. 이 규칙은 5.3절의 파서 표준 출력에서 미상 선택 키를 생략하는 규칙과 구별한다. 식별자·래퍼·처리 상태는 이 API의 기술 계약이며 LLM 출력 스키마의 속성이 아니다.

없는 과업·접근 불가·잘못된 연결은 기록을 만들지 않는 오류로 처리한다. 오류 응답은 `{error: {code, message}}`로 제안하며, `code`는 `INVALID_INPUT`, `RESOURCE_UNAVAILABLE`, `INVALID_LINK`, `STORAGE_FAILURE`로 한정한다. 권한이 없는 자원의 실제 존재 여부를 오류 내용으로 노출하지 않는다.

### 5.2 기록 저장과 선택적 맥락

`record`는 `ResearchRecord`의 속성 객체다. 필수 값은 공백이 아닌 `content_text`이며, 나머지 기존 속성은 실제로 알려진 내용만 선택 입력한다. 기록의 작성 주체를 모르면 로그인 사용자가 원저자라고 자동 채우지 않는다.

저장 후 정정 기록에는 선택적인 `revises_record_id`로 이전 기록을 지정할 수 있다. 같은 과업의 접근 가능한 기록인지 확인하고 `ResearchRecord.revises`로 연결한다. 이전 원문은 덮어쓰지 않는다.

`context`는 사용자 입력을 묶는 애플리케이션 구조로, 새로운 온톨로지 클래스가 아니다.

```text
context:
  questions: ResearchQuestion 속성 객체의 목록
  decisions: Decision 속성 객체의 목록
  document_contexts: 문헌 참조 + DocumentUse 속성 + 선택적 표현물·원문 대목의 목록
```

| 입력 항목 | 저장 규칙 |
|---|---|
| `questions` | `question_text`가 있는 항목만 만든다. 해당 과업의 질문으로 연결하고, 사용자가 이 기록에 남긴 질문임을 `documented_in`으로 연결한다. |
| `decisions` | 실제 정한 내용을 사용자가 입력한 경우만 만든다. `decision_text`가 없으면 만들지 않는다. 판단 내용은 있지만 주체·이유를 모르면 해당 선택 속성을 미상으로 두며, 그 값을 지어내지 않는다. |
| `document_contexts` | 사용자가 고른 문헌 참조와 사용 목적을 묶는다. 문헌 정체성과 과업별 목적을 같은 속성으로 합치지 않는다. |
| 선택 항목 전체 생략 | 원문 메모만 저장한다. “질문이 없음”이나 “판단을 이미 끝냄”으로 해석하지 않는다. |

문헌 맥락 한 항목의 구조는 다음과 같이 제안한다.

```text
{
  document_ref: {document_id} 또는 {document: Document의 속성 객체},
  use: DocumentUse의 속성 객체,
  artifact_ref?: {artifact_id} 또는 {artifact: DocumentArtifact의 속성 객체},
  excerpt?: EvidenceExcerpt의 속성 객체
}
```

기존 ID와 새 객체 입력은 각 참조에서 둘 중 하나만 받는다. 새 ID는 서버가 부여하며, 문헌 제목이 비슷하다는 이유로 자동 병합하지 않는다. 문헌의 실제 제목·파일 버전·위치를 모르면 추측하지 않는다. `DocumentUse.belongs_to`는 선택한 과업, `uses`는 사용자가 고른 문헌을 가리킨다.

표현물의 `represents`가 해당 문헌을 가리키는지 검사한다. 원문 대목을 저장하려면 이를 연결할 표현물이 있어야 하며, `located_in`은 그 표현물로 한정한다. 원문 구절을 확보하지 못했다면 `excerpt_text`를 생성하지 않는다. 이 과정은 **사용자 제공 정보를 등록하는 기능**이지 PDF를 가져와 분석하는 기능이 아니다.

새로 만든 맥락의 `context_refs`는 종류별 실제 ID 목록을 돌려준다. 선택 입력과 연결 중 하나라도 유효하지 않으면 그 요청 전체를 저장하지 않고 오류를 알린다. 사용자는 잘못된 선택 맥락을 빼고 원문만 저장할 수 있다. 메모만 남기는 경로에 문헌·질문·판단 입력을 강요하지 않는다.

### 5.3 다음 작업 파싱

파싱 대상은 지정된 `ResearchRecord.content_text` 한 건이다. 원문은 임의로 다듬거나 중간을 잘라 보내지 않는다. 빈 메모는 외부 호출 전에 거부하며, 현재 전송 예산으로 처리할 수 없는 메모는 조용히 절단하지 않고 사용자가 작업 한 건의 짧은 메모를 다시 남기도록 안내한다.

모델에 보내는 것은 **`parse_query.md`의 독립 마커 사이 텍스트 + 별도 출력 스키마 + 현재 메모 한 건**이다. 인터뷰, 온톨로지 전체, 저장소 지침, 정답 파일, 다른 기록을 추가로 보내지 않는다. 형식 복구 때도 같은 메모와 계약을 유지한다.

#### 모델의 출력 계약

| 속성 | 타입 | 필수 키 | 미상 처리 |
|---|---|---|---|
| `action_text` | 문자열 또는 `null` | 예 | `null` |
| `progress_text` | 문자열 또는 `null` | 아니오 | 표준 출력에서는 키 생략 |
| `blocker_text` | 문자열 또는 `null` | 아니오 | 표준 출력에서는 키 생략 |
| `deadline_text` | 문자열 또는 `null` | 아니오 | 표준 출력에서는 키 생략 |

정본은 기존 [next_action.schema.json](../src/researchtrail/schemas/next_action.schema.json)이다. Draft-07, 네 속성의 `minLength: 1`, `required: ["action_text"]`, `additionalProperties: false`를 유지한다. 새로운 enum, `intent`, `confidence`, 문헌 ID, 관계 목록을 모델 출력에 넣지 않는다.

애플리케이션은 스키마 검사 외에 공백뿐인 값, 문자열 `"null"`, 원문에 없는 구절, `action_text: null`과 다른 필드가 함께 오는 경우를 검사한다. 선택 필드의 JSON `null`은 원출력을 보존한 뒤 후속 처리에서 생략으로 정규화할 수 있다. 어느 경우에도 기존 저장값의 삭제 요청으로 해석하지 않는다.

다음은 **합성 예시**이며 실제 인터뷰나 실행 결과가 아니다.

```json
{
  "action_text": "논문 A의 표 2에서 평가 데이터 구분을 확인할 거야",
  "progress_text": "아직 시작하지 않았어",
  "deadline_text": "내일 스터디 전까지"
}
```

입력이 “지난번 하던 거 이어갈래.”라면 기대하는 모델 출력은 다음과 같다.

```json
{"action_text": null}
```

#### 애플리케이션의 응답

`candidate`는 검증된 후보 객체 또는 `null`, `attempt_count`는 실제 시도 수 0–2다. `next_action`은 애플리케이션이 계산하는 후속 처리 코드이며 도메인 클래스 `NextAction`과 구별한다.

| `next_action` | 의미 | 후속 처리 |
|---|---|---|
| `human_confirmation` | 형식·결정적 정책 검사를 통과했고 행동이 있음 | 원문과 후보를 보여 주고 의미 검토·수정·확인을 받음 |
| `clarification` | 유효한 `{"action_text": null}` | 구체적인 행동 한 건을 요청. 같은 메모 자동 재호출 없음 |
| `human_review_or_clarification` | 정책 검사에서 문제가 발견됨 | 확정 저장을 막고 입력 보완 또는 수동 검토 제공 |
| `stop` | 호출 불가·거부·복구 소진 등으로 사용할 후보를 얻지 못함 | 실패를 알리고 원문 유지, 수동 기록 경로 제공 |

`candidate: null`은 유효한 후보를 제공할 수 없다는 뜻이고, `candidate: {"action_text": null}`은 정보 수집 중인 유효한 객체라는 뜻이다.

정책 검사에 통과해도 의미가 맞다고 보증하지 않는다. 원문 속 “완료”가 다른 행동에 관한 것이라면 부분 문자열 검사는 통과할 수 있다. 사용자 확인 화면은 이 한계를 숨기지 않아야 한다.

`action_text: null`만으로 정보 부족·모호함·지원 밖 요청을 정확히 구분할 수 없다. 별도의 이유를 지어내지 말고 “기록할 구체적인 행동 한 건을 알려 주세요”라는 중립적 안내와 “연구·메일·알림을 대신 실행하지 않는 기록 기능”이라는 범위 설명을 제공한다.

기존 프롬프트의 `prepare_next_action_draft(task_id, *, action_text, progress_text=None, blocker_text=None, deadline_text=None)`는 확인용 후보를 구성하는 내부 함수 제안으로 유지할 수 있다. 이 함수와 API 응답 구성은 저장 동작이 아니다.

### 5.4 사용자 확인과 확정 저장

`reviewed_action`은 사용자 검토를 마친 네 속성의 객체다. 스키마 형식을 다시 검사하고, 확정 시에는 `action_text`가 공백이 아닌 문자열이어야 한다. `confirmed`는 명시적인 사용자 확인 동작을 나타내며 기본값을 `true`로 두지 않는다.

선택적인 `links`의 기술 필드와 도메인 관계는 다음과 같다.

| `links` 필드 | 연결되는 온톨로지 관계 |
|---|---|
| `question_ids` | `NextAction.addresses → ResearchQuestion` |
| `decision_ids` | `NextAction.based_on → Decision` |
| `artifact_ids` | `NextAction.targets_artifact → DocumentArtifact` |
| `target_record_ids` | `NextAction.targets_record → ResearchRecord` |

필수 연결은 `NextAction.belongs_to → 선택한 ResearchTask`와 `documented_in → source_record_id의 ResearchRecord`다. 선택 관계는 사용자가 지정한 기존 ID만 사용한다. 질문·판단·기록은 같은 과업에 속해야 하며, 표현물은 사용자가 선택한 해당 과업의 문헌 맥락에 연결되어 있어야 한다. ID가 없거나 접근할 수 없으면 추정해 새 객체를 만들지 않고 저장을 거부한다.

수동 입력도 같은 확인·저장 규칙을 거친다. 사용자가 후보 문장을 고쳤다면 그 문장은 사용자 편집값으로 보존하며, 원래 메모의 연속 구절이어야 한다는 **모델 추출 검사**를 그대로 적용하지 않는다. 대신 원문 메모·원래 후보·최종 편집값을 구분하고, 사용자가 편집한 내용을 추출 성공 사례로 계산하지 않는다.

확인 요청에는 과업 선택을 고정한다. 다른 과업으로 바꾸려면 확인 화면에서 다시 검토하게 한다. 같은 확인 동작의 재전송으로 작업이 중복 생성되지 않도록 애플리케이션이 확인 요청 식별자를 관리한다. 이는 모델 출력에 추가할 필드가 아니다.

저장 후 내용을 고칠 때 원문을 몰래 덮어쓰지 않는다. 이 첫 버전은 **확정 전 수정**을 기본으로 하며, 저장 후 정정은 새 기록으로 남긴다. 이전 기록을 정정 대상으로 명시한 경우만 `ResearchRecord.revises`를 연결하고, 그 관계만으로 기존 `NextAction`·외부 사본을 자동 갱신하지 않는다.

### 5.5 재개 조회

`GET /tasks/{task_id}/resume`는 저장소에 존재하고 접근 가능한 데이터만 돌려준다.

| 응답 요소 | 내용 |
|---|---|
| `task` | 해당 과업의 목표·범위·현재 서술 |
| `records` | 이 과업에 속한 기록. 원문과 작성·검토·채택 상태를 혼동하지 않음 |
| `context` | 저장된 질문·판단·문헌 사용 맥락 및 연결한 자료 위치 |
| `next_actions` | 이 과업에 연결된 사용자 확인 완료 작업, 원문 기록 ID와 실제 선택 관계 |

최근 저장한 기록을 먼저 보여 주되, 사용자가 내용을 추가로 열어 볼 수 있어야 한다. 문헌의 최근 버전이나 판단의 최종성을 저장 순서에서 추론하지 않는다.

자료 위치가 있으면 기록된 링크·판본·표·식 번호 등의 단서를 보여 준다. 지정한 구절로 자동 이동하거나 내용이 주장을 뒷받침한다고 보증하지 않는다. 링크가 열리지 않는 경우에는 기록된 위치를 유지하며, 원문이 원래 존재하지 않는다고 결론 내리지 않는다.

저장되지 않은 값은 “미기록/확인 필요”로 보여 준다. 빈 배열은 등록된 항목이 없다는 뜻일 뿐 실제 질문·판단·장애가 없다는 뜻이 아니다. 다른 과업의 내용이나 모델 생성문으로 빈자리를 채우지 않는다.

### 5.6 정정·부분 구현의 경계

이 인터페이스는 도메인 전체를 구현하는 범용 편집기를 요구하지 않는다. 생성·확인·재개에 필요한 관계부터 구현한다. 외부 자료 다운로드, 자동 사건 추적, 전역 중복 제거, 전체 수정 전파와 협업 기능은 이 버전의 완료 조건에 넣지 않는다.

단, 기능을 줄이면서 “원문 보존”, “사용자 확인 전 확정 금지”, “과업별 분리”, “미상 값 생성 금지”를 삭제해서는 안 된다. 범위가 달라지면 먼저 이 문서를 검토·변경하고 테스트와 구현에 반영한다.

## 6. 수용 기준과 검증

### 6.1 판정 원칙

아래 AC는 EARS 형태의 **조건–시스템–동작**으로 쓴 검토 후보다. 모든 AC는 아직 제품 전체의 통과 판정을 받지 않았다. 기존 오프라인 검사는 일부 하위 로직의 근거이며 저장·조회·사용자 효과까지 증명하지 않는다.

원문 구절 포함 여부는 결정적 검사로 확인할 수 있지만, 행동·상태의 의미상 귀속은 사람이 확정한 기준 사례로 따로 판정한다. 사용자가 잘못된 후보를 고쳐 저장했다면 **저장 흐름은 성공할 수 있지만 최초 추출은 실패**로 기록한다.

<a id="ac1"></a>
### AC1 — 출력 구조와 결정적 정책 검사 [상시 적용]

**다음 작업 후보를 다룰 때, ResearchTrail은 기존 네 필드 스키마와 결정적 정책 검사를 통과한 결과만 정상 후보로 취급한다.**

- **Given:** 필수 키 누락, 숫자형 행동·기한, 빈 문자열, 미정의 키, 공백뿐인 값, 문자열 `"null"`, null 행동에 다른 필드가 붙은 검증용 입력.
- **When:** JSON·스키마·정책 검사를 수행한다.
- **Then:** 각 오류를 해당 검사 단계에서 식별하고 확정 저장으로 전달하지 않는다. 유효한 `{"action_text": null}`은 오류가 아닌 재질문 대상으로 분리한다.
- **판정:** 경계 사례별 기대 단계·후속 동작의 일치. JSON 형식 성공률과 정책 통과율을 따로 기록한다.
- **현재 근거:** 기존 러너의 `missing_action`, `numeric_action`, `extra_intent`, `whitespace`, `null_with_deadline` 등 오프라인 검사. 제품 연결 테스트는 예정.

<a id="ac2"></a>
### AC2 — 정보 부족·모호함의 처리 [예외 대응]

**행동과 대상을 특정할 수 없거나 여러 독립 행동 중 기록할 한 건이 선택되지 않았을 때, ResearchTrail은 작업을 확정하지 않고 구체적인 행동을 다시 묻는다.**

- **Given:** “지난번 하던 거 이어갈래.”, 대상이 모호한 메모, 우선 행동이 선택되지 않은 복수 작업 메모.
- **When:** 파싱 결과가 `{"action_text": null}`이다.
- **Then:** 같은 입력을 자동 재호출하지 않고 원문을 유지하며 재질문한다. 확정된 `NextAction` 저장 건수는 0이다.
- **판정:** 알려진 모호·복수 작업 사례에 대한 모델 출력, 호출 횟수, 저장소 변화, 안내 문구를 각각 검사한다. 구체적 행동이 없는 예시에 null을 출력하는 품질과 null 이후의 애플리케이션 동작을 구별한다.
- **현재 근거:** `null_clarification`, `null_no_retry` 등 오프라인 하위 검사. 실제 모델의 모호성 처리와 화면·저장 차단은 미검증.

<a id="ac3"></a>
### AC3 — 행동·상태·장애·기한의 의미 보존 [상시 적용]

**메모에서 다음 작업을 추출할 때, ResearchTrail은 그 작업에 실제로 귀속되는 표현만 보존하고 다른 행동의 완료, 추측한 장애, 계산한 날짜를 덧붙이지 않는다.**

- **Given:** “논문 읽기는 완료. 표 2 확인은 아직 시작하지 않았어.”와 다음 작업을 명시한 메모, 상대 기한이 있는 메모, 상태값을 강제로 넣으라는 지시가 섞인 메모.
- **When:** 모델이 후보를 반환한다.
- **Then:** 논문 읽기의 완료를 표 확인의 완료로 사용하지 않는다. 상대 기한은 원문으로 보존한다. 주입된 지시문을 실제 진행 상태로 채택하지 않는다.
- **판정:** 사람이 확정한 행동·귀속·부정·조건·미상 항목 기준을 모두 만족하면 해당 사례를 통과로 센다. 잘못된 후보가 형식 검사를 통과해도 추출 실패다. 확인 화면은 원문과 후보를 함께 보여 주며 자동 저장하지 않는다.
- **현재 근거:** `wrong_attribution` 검사는 오히려 부분 문자열 검사만으로 이 오류를 막을 수 없음을 보여 준다. 의미 정확도의 통과 근거는 아직 없다.

<a id="ac4"></a>
### AC4 — 사용자 확인과 원문·과업 연결 [이벤트 기반]

**사용자가 작업 저장을 확인할 때, ResearchTrail은 구체적인 행동·접근 가능한 과업·원문 기록·선택 관계를 검증한 뒤에만 확정된 `NextAction`을 저장한다.**

- **Given:** 같은 과업의 원문 기록과 정상 후보, 또는 확인 없음·null 행동·타 과업 기록·없는 ID의 오류 입력.
- **When:** 확정 저장을 요청한다.
- **Then:** 정상 입력은 원문과 최종 값을 구분해 한 건 저장한다. 오류 입력과 확인 취소는 작업을 저장하지 않는다. 동일 확인 요청 재전송도 중복 저장하지 않는다.
- **판정:** 저장 전후의 레코드 수·값·관계와 재조회 결과 비교. 사용자 수정은 모델 추출 결과와 구별한다.
- **현재 상태:** 확정 저장 구현·통합 테스트 예정. 현재 러너는 이 기능을 수행하지 않는다.

<a id="ac5"></a>
### AC5 — 같은 과업의 맥락 재열람 [이벤트 기반]

**사용자가 문헌 과업을 다시 열면, ResearchTrail은 해당 과업에 저장된 기록·맥락·확인된 작업을 함께 반환하고 다른 과업의 기록을 섞지 않는다.**

- **Given:** A·B 두 과업에 서로 다른 기록·목적·질문·판단·작업이 있고, 일부 기록의 저장 시각이 같다.
- **When:** A의 재개 조회를 요청한다.
- **Then:** A의 내용과 허용된 자료 참조만 반환한다. 정렬 규칙은 4.3절을 따르며 LLM 호출은 0회다. 저장 순서를 판단의 실제 발생 순서로 표시하지 않는다.
- **판정:** 결과 ID 집합·연결·정렬·원문 대조, 외부 호출 감시. 실제 원문을 검토하기 위한 링크 열람은 실패로 간주하지 않는다.
- **현재 상태:** 조회 구현·통합 테스트 예정.

<a id="ac6"></a>
### AC6 — 미기록·미확인·판단 없음의 보존 [상시 적용]

**목적·질문·판단·위치·상태가 기록되지 않았거나 확인되지 않았을 때, ResearchTrail은 그 한계를 표시하고 확정 내용으로 채우지 않는다.**

- **Given:** 실제 판단이 없는 과업, 제목 또는 원문 위치가 미상인 자료, 검토되지 않은 AI 설명, 내용만 있는 최소 메모.
- **When:** 기록을 저장하거나 재개 화면에 표시한다.
- **Then:** 메모만 저장할 수 있고, 미기록 내용은 “미기록/확인 필요”로 표시한다. `Decision`을 임의 생성하거나 읽음·저장·링크 존재를 질문 해결·검증 완료로 전환하지 않는다.
- **판정:** 생성 객체·표시 값·원문과의 대응 검사. 외부 링크가 있다는 사실과 의미상 근거가 있다는 주장을 별도로 점검한다.
- **현재 상태:** 도메인 규칙과 관련 프롬프트는 제공되어 있으나 제품 동작은 미검증.

<a id="ac7"></a>
### AC7 — 실패·재시도·범위 밖 요청의 통제 [예외 대응]

**형식 오류·호출 실패·지원 밖 요청이 발생하면, ResearchTrail은 정해진 한도에서만 복구하고 원문 메모를 유지하며 연구나 외부 작업을 대신 실행하지 않는다.**

- **Given:** JSON 절단·스키마 오류, 반복 형식 오류, 인증·통신 오류, 모델 거부, 직접 실행 요청과 메모가 섞인 입력.
- **When:** 파싱 흐름을 수행한다.
- **Then:** 형식 오류만 추가 한 번 복구한다. 정보 부족·정책 또는 의미 문제·인증 실패·거부에는 형식 복구를 반복하지 않는다. 상한 이후 자동 호출·자동 저장을 멈추고 수동 기록 또는 보완을 안내한다. 메일·학습·알림·코드 실행은 0회다.
- **판정:** 합성 응답으로 분기·횟수·시간·저장 변화를 확인하고, 실제 모델 출력의 범위 준수는 별도로 검토한다. 예상치 못한 도구 호출은 실행하지 않는다.
- **현재 근거:** `repair_once`, `repair_limit`, `auth_no_retry`, `refusal_no_retry`, `transport_no_retry`, `time_budget`, `request_isolation_*` 등 오프라인 검사. 제품 UI·영속 저장 통합은 미검증.

### 6.2 AC와 테스트의 연결

아래 경로와 케이스 ID는 **후속 구현 제안**이다. 실제 파일 존재·실행·통과를 주장하지 않는다. 기존 테스트가 있으면 이를 확인한 뒤 중복을 피하고, 판정 기준 변경은 사람 승인을 받는다.

### 6.3 실제 모델 실험과 기술 스파이크

기존 여덟 자연어 입력은 프롬프트의 예시·실패 모드에서 가져온 **개발·회귀 사례**다. 이를 아직 보지 않은 평가 데이터라고 부르지 않는다. 실험을 수행한 뒤 최초 출력과 형식 복구 출력, 구조·정책 판정과 사람의 의미 판정을 분리해 기록한다.

**최고 위험 가정의 후보:** 짧은 연구 메모에서 다음 행동과 그 행동의 상태·장애·기한을 잘못 귀속하지 않고, 사용자 검토 부담을 감당할 수 있는 수준으로 추출할 수 있는가.

이 가정의 실패 영향은 사용자가 잘못된 다음 작업을 확인하거나 계속 수정해야 하는 데 있다. 현재 근거의 공백은 실제 모델 출력의 의미 판정이 없다는 점이다. 대안은 수동 입력이지만, 그 대안에서는 AI가 입력 부담을 줄인다는 제안의 이득을 다시 검토해야 한다.

정식 스파이크는 초안 승인 뒤 `docs/spikes/next_action_attribution.md`에 기록하는 방식을 제안한다. 실행 전에 평가 단위·미사용 평가 자료·건별 판정·합격선·시간 제한을 사람이 정한다. 두 사람이 독립적으로 만든 기준을 합의하고, 고정된 모델·프롬프트·설정으로 평가한다. 지금 문서에 결과나 합격선을 사후로 꾸며 넣지 않는다.

| 결과 | 이 스펙에 반영할 결정 |
|---|---|
| 기준을 충족함 | 사용자 확인을 유지한 제한적 추출 기능의 채택 검토 |
| 기준에 미달함 | 자동 추출 방법 변경 또는 수동 입력 중심으로 범위 조정. AI 기능의 채택 여부를 명시적으로 재검토 |
| 실행·자료가 부족함 | 판단 보류. 구현 가능성과 정확도를 검증 완료로 표시하지 않음 |

단순히 수동 입력을 제공한다고 AI 제품의 핵심 가설까지 검증된 것은 아니다. 방식 변경이 필요하면 문제–해결 가설–핵심 기능의 연결도 함께 검토한다.
