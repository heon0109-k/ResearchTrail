# 질문하기: 연결 논문 범위·임베딩 검색 변경안

상태: 2026-11-27 사용자 요청에 따라 정리한 변경안 초안. 계산 부분, 논문 연결 저장, 색인 저장, 색인 경로와 임베딩 호출까지 구현했고(6.1절) 원본 SPEC·온톨로지·설정·기존 테스트는 바꾸지 않았다. 팀의 제품 명세 승인과 백엔드 담당자 확인은 별도다. 아래 숫자 중 "측정 후 확정"이라고 적은 값은 실측값이 아니다.

## 1. 제안 요약

[단일 PDF 변경안](single_pdf_rag.md)의 질문하기를 다음과 같이 넓힌다.

- 검색 범위를 열어 둔 논문 한 편에서, **현재 논문과 연결로 이어진 논문**으로 넓힌다. 한 번의 질문에서 검색하는 문서는 현재 논문과 연결 논문 최대 8편이다.
- 검색 방식에 **임베딩 유사도**를 추가한다. 한국어 질문과 영어 본문이 글자로는 겹치지 않는 문제를 줄이기 위해서다.
- 분할한 구절과 벡터를 **서버 PostgreSQL에 저장**한다. 다른 기기에서 로그인해도 질문하기가 동작해야 하기 때문이다.

다음 할 일 파싱과 재개 조회는 지금처럼 RAG 없이 동작한다. 이 변경안은 실험 기능인 질문하기에만 해당하며 MVP 평가 AC에 포함하지 않는다.

## 2. 전제

- 여러 사람이 각자 로그인해 자기 기록만 남긴다. 공유·협업은 없다.
- 백엔드는 다른 담당자가 만든다. 2026-11-27 main(PR #22) 기준으로 Supabase를 쓴다: PostgreSQL(`supabase/migrations/`), 자바스크립트 Edge Function(`supabase/functions/researchtrail/`), Google 로그인, 비공개 PDF 저장소. Vercel에는 `npm run build`로 만든 화면 파일만 올린다.
- Edge Function은 요청 사이에 메모리가 유지되지 않고 요청 크기·실행 시간에 제한이 있다. 그래서 색인은 DB에 두고, PDF 글자 추출은 브라우저에서 한다.
- 같은 날 확인한 결과, 계정 화면에는 **논문 연결과 질문하기 UI가 없다**. 둘 다 로그인 없는 브라우저 전용 작업공간에만 있다. 서버의 연결 저장은 PR #23에서 추가했다(`/tasks/{task_id}/paper-links`). 이 변경안의 범위 규칙(3.1절)을 계정에서 쓰려면 계정 화면의 연결·질문하기 UI가 더 필요하다(8절).

## 3. 결정 사항

### 3.1 검색 범위

- 범위는 논문 연결 그래프에서 현재 논문이 속한 연결 요소다. 연결 방향은 무시한다. 다른 사용자의 논문과 연결되지 않은 논문은 검색하지 않는다.
- 검색 문서는 현재 논문 + 연결 논문 최대 8편(합계 최대 9편)이다. 색인이 완료된 논문만 센다.
- 8편을 고르는 순서는 다음과 같다. 같은 질문·같은 연결 상태에서는 항상 같은 논문이 뽑혀야 한다.
  1. 현재 논문에서의 거리(최단 경로의 연결 수)가 짧은 순
  2. 거리가 같으면 질문과의 관련도가 높은 순. 관련도는 질문과 그 논문의 제목·초록·연결 이유를 비교해 구한다.
  3. 관련도도 같으면 논문 ID 오름차순
- 범위는 질문할 때마다 그 시점의 연결로 계산한다. 응답을 기다리는 동안 연결이나 열린 논문이 바뀌면 그 응답은 버린다.
- 상한 때문에 빠진 논문, PDF가 없는 논문, 색인이 끝나지 않은 논문은 화면에 표시한다.

### 3.2 추출·분할

- 브라우저가 PDF.js로 쪽별 글자를 추출하고 분할한다. 방식과 상수(쪽 단위, 1,600자, 320자 겹침)는 지금의 `web/js/chat-retrieval.js`를 그대로 쓴다.
- 브라우저는 구절(쪽 번호, 쪽 안의 시작·끝 위치, 본문)을 여러 요청으로 나눠 서버에 보낸다.
- 한 번 색인한 논문은 다시 추출·분할하지 않는다. 다시 하는 경우는 PDF 교체, 중단된 업로드, 분할 방식이나 임베딩 모델 변경뿐이다.
- 글자 인식(OCR)은 하지 않는다. 글자를 읽지 못한 PDF는 색인 실패로 알린다.

### 3.3 저장과 색인 상태

- 구절과 벡터는 서버 PostgreSQL(pgvector)에 저장한다. RAG 전용 테이블은 `rag_` 접두어로 구분하며 백엔드 테이블에는 쓰지 않는다. 아래는 기술 테이블 초안이며 온톨로지 속성이 아니다.

| 테이블(가칭) | 담는 것 |
|---|---|
| `rag_chunks` | 소유자, 논문, 쪽 번호, 시작·끝 위치, 본문, 벡터 |
| `rag_paper_index` | 소유자, 논문, 색인 상태(안 됨·진행 중·완료), PDF 지문, 분할·임베딩 설정 버전, 관련도 계산용 논문 벡터 |

- 논문을 삭제하면 그 논문의 구절과 벡터도 지운다. PDF 지문이 달라지면 기존 구절을 지우고 다시 색인한다.
- 업로드가 끊기면 "진행 중"으로 남기고 다시 올릴 때 처음부터 교체한다. 진행 중인 논문은 검색 대상이 아니다.
- 서버가 원본이고 브라우저는 따로 저장하지 않는다. 오프라인 편집 후 병합은 범위 밖이다.
- PDF 파일은 백엔드가 이미 비공개 저장소에 보관한다(한 개당 최대 10 MiB). 색인 단위는 업로드된 PDF 판본(`DocumentArtifact`)이고, PDF 지문은 그 판본에 저장된 SHA-256을 쓴다.
- pgvector 확장을 켜는 마이그레이션은 백엔드의 DB 검사(`tests/run_account_db.py`)가 모든 마이그레이션을 실행하므로 그 검사 환경에도 영향을 준다. 추가 전에 담당자와 맞춘다(8절).

### 3.4 검색과 전송 예산

- 구절 순위는 기존 키워드 점수와 임베딩 유사도를 합쳐 정한다. 결합 방식과 가중치는 측정 후 확정한다.
- 기존 키워드 검색과 쪽 우선 규칙(명시한 쪽, 선택한 문장, "이 쪽", 요약 질문의 1쪽)은 유지하며 현재 논문에만 적용한다.
- 질문에 "그림 3", "Figure 3"처럼 번호가 있으면 그 캡션과 언급 문장을 먼저 고른다.
- 한 번의 질문에 모델로 보내는 구절 수와 글자 수는 계속 제한한다. 지금 값(구절 6개, 1만 자)은 단일 PDF 기준이므로 새 값은 측정 후 확정한다.
- 한 논문에서 뽑는 구절 수에도 상한을 둔다. 긴 논문 하나가 예산을 독점하지 않게 하기 위해서다.
- 한국어 질문의 영어 검색어 확장 단계는 임베딩 도입 뒤 필요한지 측정해 유지 여부를 정한다.

### 3.5 답변과 근거

- 모델에 보내는 구절에는 문서 표시와 쪽 번호를 붙인다(예: `[문서 A · p.3]`). 내부 ID는 모델에 보내지 않고, 문서 표시와 논문의 대응은 애플리케이션이 관리한다.
- 근거는 `{문서, 쪽, 인용}`으로 받고, 인용이 그 문서 그 쪽의 저장된 구절에 실제로 있는지 검사한다. 통과한 근거만 링크로 만든다.
- 여러 논문을 비교하는 답은 논문마다 근거를 받는다. 확인되지 않은 논문에 대한 서술은 답으로 통과시키지 않는다.
- 근거를 찾지 못하면 "검색한 구절에서 근거를 찾지 못했다"고 안내한다. "연결된 논문 전체에 없다"고 단정하지 않으며, 검색에서 빠진 논문이 있으면 함께 알린다.
- 인용 일치는 답변 의미의 정확성을 보증하지 않는다는 기존 한계는 그대로다.

### 3.6 그림

- 그림 이미지를 모델에 보내지 않는다. 캡션과 본문 설명으로만 답한다.
- 그림을 봐야만 알 수 있는 질문에는 추측하지 않고 근거 부족으로 답한다.
- 질문 입력란 근처에 "그림 속 내용은 읽지 못하고 캡션과 본문 설명으로 답한다"는 안내를 둔다.

### 3.7 동의와 전송

- 임베딩을 만들려면 색인하는 논문의 본문 전체가 외부 임베딩 서비스로 전송되고, 구절이 팀 서버에 저장된다. 지금의 "검색 구절만 전송"과 달라지므로 동의 문구와 범위를 바꾼다.
- 질문 전에 이번 검색에 포함되는 논문 목록을 보여 준다.
- 미동의 시 색인·검색·답변 호출을 하지 않는 기존 규칙은 유지한다. API 키는 서버에만 둔다.

## 5. 서버 경로 초안

경로 이름과 형식은 백엔드 담당자와 맞춘 뒤 확정한다. 오류 응답은 기존 계약 `{error: {code, message}}`와 코드 네 개를 따르고, 권한 없는 논문의 존재 여부를 노출하지 않는다.

| 동작 | 입력 | 출력 |
|---|---|---|
| 색인 시작 | 논문 ID, PDF 지문 | 색인 상태. 기존 구절은 교체 대상이 됨 |
| 구절 올리기 | 논문 ID, 구절 묶음(쪽, 위치, 본문) | 받은 구절 수 |
| 색인 완료 | 논문 ID, 전체 구절 수 | 색인 상태. 수가 맞지 않으면 완료로 바꾸지 않음 |
| 색인 상태 조회 | 논문 ID 목록 | 논문별 상태 |
| 질문하기 | 현재 논문 ID, 질문, 현재 쪽, 선택한 문장, 이전 대화 | 답, 검증된 근거(논문·쪽), 검색한 논문 목록, 빠진 논문 목록 |

## 6. 코드 위치

- RAG 서버 코드는 자바스크립트로 `supabase/functions/_rag/`에 둔다. 따로 배포하는 함수가 아니라 기존 `researchtrail` 함수가 불러 쓴다. 로그인 확인과 오류 변환을 한 곳에서 하기 위해서이며, 기존 파일에는 경로 연결만 추가한다.
- 백엔드에서 받는 것은 다섯 가지다: 현재 사용자 확인, 논문·연결 읽기, DB 사용 방식, OpenAI 호출 통로, 경로 등록. RAG는 백엔드 테이블을 읽기만 한다.
- 브라우저 쪽은 새 파일로 추가하고, 테스트도 새 파일로 추가한다.

### 6.1 구현 현황 (2026-11-27)

계산 부분과 DB 저장 부분을 만들었다. 계산 부분은 배포되는 함수가 아니며(`_`로 시작하는 폴더), 아직 어디에서도 호출하지 않는다. DB 부분은 임시 PostgreSQL에서만 검사했고 실제 Supabase 프로젝트에는 적용하지 않았다.

| 파일 | 하는 일 | 대응 절 |
|---|---|---|
| `supabase/functions/_rag/scope.mjs` | 연결 그래프에서 현재 논문 + 연결 논문 최대 8편 고르기, 빠진 논문과 이유 보고 | 3.1 |
| `supabase/functions/_rag/ranking.mjs` | 키워드·임베딩 순위 결합, 전송 예산, 논문당 상한, 그림 번호 우선 | 3.4 |
| `supabase/functions/_rag/answer.mjs` | 문서 표시가 붙은 프롬프트 조립, 논문별 인용 검증 | 3.5, 3.6 |
| `tests/rag_scope.test.mjs`, `tests/rag_ranking.test.mjs`, `tests/rag_answer.test.mjs` | 위 세 파일의 고정 입력 검사 27건 (팀 승인 전 초안) | 7절 L1~L6, L9 |
| `supabase/migrations/20261127000700_paper_links.sql` | 과업 안 논문 연결의 저장·조회 (PR #23) | 3.1, 8절 1번 |
| `supabase/migrations/20261127000800_rag_index.sql` | 색인 상태 표와 구절·벡터 표(pgvector), 색인 시작·구절 올리기·색인 완료·상태 조회 | 3.3, 5절 |
| `tests/sql/account_paper_links.sql`, `tests/sql/account_rag_index.sql` | 위 두 마이그레이션의 DB 검사 (팀 승인 전 초안) | 7절 L1, L7 일부 |
| `supabase/functions/_rag/embedding.mjs` | 구절 본문을 임베딩 서비스로 보내 벡터로 바꾸고, 개수·순서·크기를 확인 | 3.3, 3.7 |
| `supabase/functions/_rag/index-route.mjs` | 색인 경로: `GET /tasks/{task_id}/rag-index`, `POST /tasks/{task_id}/artifacts/{artifact_id}/rag-index/{begin,chunks,finish}` | 5절 |
| `tests/account_rag_index_edge.test.mjs` | 색인 경로의 가짜 전송 검사 8건 (팀 승인 전 초안) | 7절 L7, L10 일부 |

순위 결합은 순위 역수 합(RRF) 방식, 전송 예산은 기존 단일 PDF 값(구절 6개, 1만 자)에 논문당 2개 상한을 둔 초안이다. 측정 후 확정한다. 색인 저장의 벡터 크기(1536), 묶음당 구절 수(100), 판본당 구절 수 상한(5,000), 구절 길이 상한(4,000자)도 초안 값이다. 색인 시작은 요청에 `consent: true`가 있어야 하고, 구절은 시작된 색인이 확인된 뒤에만 임베딩 서비스로 나간다. 임베딩 모델 이름(`text-embedding-3-small`), 요청당 구절 수(32), 대기 시간(30초)은 초안 값이며 실제 서비스 호출은 한 번도 하지 않았다. 미구현: 벡터 유사도 검색, 질문 HTTP 경로, 브라우저 연결, 동의 화면, 사용자별 호출 한도. 7절의 L7 중 PDF 교체 후 재색인, L8·L10·L11은 이 부분이 생긴 뒤에 검사할 수 있다.

DB 검사(`tests/run_account_db.py`)에는 이제 pgvector가 필요하다. Homebrew의 pgvector는 PostgreSQL 18·19용이라 로컬 검사는 PostgreSQL 18로 돌렸다(`brew install postgresql@18 pgvector`). Supabase의 PostgreSQL 17에서의 동작은 미검증이다.

## 7. 검증 사례 초안

팀 승인 전 초안이다. 기존 승인 테스트와 골든 케이스는 고치지 않으며, 아래 통과를 제품 수용 완료나 실제 모델 성능으로 세지 않는다. 근거는 절대 규칙 1·5와 SPEC AC6·AC7, NF3·NF6, AGENTS 5절의 결정적 정렬이다.

| 사례 | 기대 결과 |
|---|---|
| L1 범위 밖 차단 | 현재 논문과 연결되지 않은 논문, 다른 사용자의 논문의 구절은 검색·전송되지 않는다. |
| L2 여러 단계 연결 | 세 단계 떨어진 논문의 구절이 검색된다. |
| L3 상한과 순서 | 연결 논문이 8편을 넘으면 거리 → 관련도 → ID 순으로 8편만 고른다. 같은 입력에서 결과가 같다. |
| L4 빠진 논문 표시 | 상한 초과·PDF 없음·색인 미완료 논문을 표시하고, 근거 부족 안내에서 이를 알린다. |
| L5 출처 검사 | 다른 논문의 구절을 인용으로 붙이거나 보낸 적 없는 쪽을 인용하면 답으로 통과시키지 않는다. |
| L6 비교 답 | 두 논문을 비교하는 답에서 한 논문의 근거가 확인되지 않으면 그 서술을 통과시키지 않는다. |
| L7 색인 상태 | 업로드가 끊긴 논문은 완료로 보이지 않고 검색되지 않는다. PDF 지문이 바뀌면 다시 색인한다. |
| L8 늦은 응답 | 연결·열린 논문이 바뀐 뒤 도착한 응답은 표시·저장하지 않는다. |
| L9 그림 질문 | 본문에 근거가 없는 그림 질문은 근거 부족으로 처리한다. |
| L10 동의 | 미동의 시 구절 전송·임베딩·답변 호출이 0회다. |
| L11 한국어 질문 | 한국어 질문으로 영어 본문의 해당 구절이 검색되는지 사람이 정한 사례로 확인한다. 실제 모델·임베딩 품질은 별도 관찰한다. |

## 8. 확인이 필요한 것

백엔드 담당자 (서버 언어, 로그인 방식, PDF 보관은 2026-11-27 코드에서 확인해 목록에서 뺐다):

1. 논문 연결의 이름. 저장은 과업 안의 `DocumentUse` 사이로 구현했다(PR #23). 온톨로지에 논문 간 관계가 없어 `document_use_links`, `reason_text`는 초안 이름이다. 연결의 수정·삭제 방식도 정해야 한다.
2. 계정 화면에 연결 만들기와 질문하기 UI를 누가 어디에 넣을지. 지금 계정 화면의 PDF 읽기 화면에는 질문하기가 없다.
3. pgvector 확장을 쓰기로 했다(2026-11-27). DB 검사를 돌리는 환경마다 pgvector가 필요하므로(6.1절) 담당자의 검사 환경을 맞춰야 한다. 어렵다면 벡터를 실수 배열로 저장하고 SQL로 유사도를 계산하는 방식이 대안이다.
4. OpenAI 키를 함수 비밀값 `OPENAI_API_KEY`로 등록하는 절차(임베딩 모델은 `RAG_EMBEDDING_MODEL`로 바꿀 수 있다). 함수는 따로 등록하지 않고 기존 `researchtrail` 함수에 넣었다.
5. Edge Function의 요청 크기·실행 시간 한도. 지금 답변 요청은 최대 120초까지 기다린다.
6. 판본을 지우면 색인과 구절도 함께 지워지도록 `document_artifacts`에 외래 키를 걸었다. 이 방식이 괜찮은지
