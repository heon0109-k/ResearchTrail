# 다음 작업 귀속 검증 계획

작성 2026-11-07 · 수정 2026-11-08. 실행 전 계획 초안이다. 성공 조건·시간 예산은 팀 확정 전이며 실제 모델 호출과 사람의 의미 판정은 미수행이다.

## 1. 가장 위험한 가정

**메모 한 건에서 다음 행동과 그 행동에 실제로 속한 진행 상태·장애·기한만 추출하고, 다른 행동의 완료나 지시문을 해당 작업의 사실로 잘못 붙이지 않을 수 있는가.**

- 실패 영향: 잘못된 후보는 사용자의 수정·검토를 요구하고 잘못된 작업 확정을 유발할 수 있다. 확인 버튼이 있다는 사실만으로 최초 추출 오류가 해결되지는 않는다.
- 근거 부족: 현재 앱은 규칙 기반으로 행동 한 줄을 제안한다. Python policy.py는 구조·원문 구절 검사만 수행한다. 실제 모델의 네 필드 의미 정확도는 검증하지 않았다.
- 대체 비용: 현재 앱의 직접 입력·수정·취소와 규칙 기반 예시를 유지할 수 있다. 다만 사람이 직접 적어야 하므로 AI가 입력 부담을 줄인다는 이득은 입증되지 않는다.
- 우선순위: 브라우저 저장·재개 오류는 결정적 회귀 검사로 확인할 수 있지만, 다른 행동의 상태를 잘못 귀속하는 문제는 스키마·부분 문자열 검사만으로 확인할 수 없어 우선 검증 대상으로 둔다.

**구현 경계:** 이 스파이크는 향후 실제 모델을 연결할지 결정하기 위한 실험이다. 현재 앱에 진행·장애·기한 입력칸이나 서버를 추가하는 작업이 아니다. 통과해도 실제 모델 연결·서버 저장·접근 제어의 구현 완료를 뜻하지 않는다. 사용자 재개 효과는 [PROBLEM 5.2절](../PROBLEM.md)의 별도 관찰로 판단한다.

## 2. 시간 제한

다음 예산은 실행 전 팀 확정이 필요한 제안이다.

| 범위 | 상한·종료 조건 |
|---|---|
| 실험 전체 | 사례 준비·독립 라벨·합의·모델 호출·결과 정리를 포함한 누적 작업 시간 2시간. 상한 도달 또는 결과 정리 완료 중 먼저 오는 시점에 중단 |
| 호출 1회 | 최대 20초 |
| 메모 1건 | 최초 호출과 형식 복구를 합해 최대 40초·2회. 정책 오류·null·거부·통신 오류는 형식 복구 대상으로 삼지 않음 |
| 평가 실행 전체 | 고유 메모 20건을 각 1회 평가. 형식 복구 포함 최대 40회 호출, 회당 출력 상한 512토큰, 예약 출력 예산 최대 20,480토큰 |

실험 전체 시간은 작업 구간별 시작·종료와 누적 시간을 기록한다. 제한에 닿으면 사례나 합격선을 줄여 통과시키지 않고 부분 결과와 미완료 이유를 보고한다. 비용은 실제 사용량이 있을 때 별도로 기록하며 금액을 추측하지 않는다. 추가 실행은 같은 회차의 연장으로 숨기지 않고 재도전 계획으로 분리한다.

## 3. 성공 조건

### 평가 단위와 자료

- 평가 단위는 고유 메모 한 건의 **최초 원출력**이다. 형식 복구 결과와 사용자 편집값은 별도 기록하고 최초 성공으로 바꾸지 않는다.
- 프롬프트·스텁 작성이나 수정에 사용하지 않은 **새 합성 메모 20건**을 평가용으로 준비한다. 현재 미작성이다. 원문은 메모 한 건만 보내며 실제 인터뷰 원응답·비공개 연구 메모는 사용하지 않는다.
- [semantic_cases_draft.yaml](../research/semantic_cases_draft.yaml)의 NA-SEM-01~04는 이미 검토·개발에 사용했으므로 개발 회귀 자료로만 둔다. 이 파일의 CONTEXT 사례는 AC6 자료이며 모델 의미 평가 20건에 포함하지 않는다.
- 평가 자료는 ① 행동 간 상태 귀속 ② 부정·미상·장애 ③ 상대 기한 ④ 모호·복수 작업 ⑤ 인용된 지시문을 각 4건씩 포함한다. 배치는 제안이며 실제 사례와 사람 기대값을 작성한 뒤 실행 전에 동결한다.

### 건별 판정 규칙

사람이 합의한 허용 원문 구절·선택 필드·금지 추론을 모두 만족하고 구조·결정적 정책 검사도 통과하면 1건 성공으로 센다. action_text만 맞거나 일부 필드를 놓친 경우는 성공이 아니다.

- 행동은 메모의 연속 구절이며 사람이 허용한 행동과 일치해야 한다. 허용 가능한 표현이 여러 개면 호출 전에 각각의 원문 구절을 명시한다.
- 진행·장애·기한은 해당 행동에 귀속되는 원문 구절만 포함한다. 없는 선택 필드는 생략하고, 선택 null의 정규화는 SPEC 5.3절을 따른다. 상대 기한을 달력 날짜로 계산하지 않는다.
- 유효한 정보 부족 사례는 action_text: null만 허용한다. 선택 필드를 함께 붙이거나 행동을 추측하면 실패다.
- 다른 행동의 완료, 없는 장애·기한, 지시문 속 상태를 실제 사실로 채택한 출력은 중대 오류로 기록한다.
- 잘린 출력·형식 오류·호출 실패는 최초 성공이 아니다. 형식 복구 성공률은 별도로 보고한다. 미판정은 성공으로 세지 않는다.

### 합격선 제안

최초 출력 20건 중 **18건 이상 성공**, **중대 오류 0건**을 모두 만족해야 잠정 채택 검토 대상으로 삼는다. 중대 오류가 1건이라도 있으면 미달이다. 20건 전체 실행 또는 사람 판정을 완료하지 못하면 부분 성공률만으로 통과시키지 않고 판단을 보류한다.

18/20과 중대 오류 0건은 기존 계획에서 유지한 팀 검토 전 제안값이다. 합격선과 건별 기대값은 사람이 실행 전에 확정해야 하며 결과를 보고 낮추지 않는다.

## 4. 방법

1. **사람 기준 만들기:** 팀원 2명이 같은 20건에 대해 서로의 답과 모델 출력을 보지 않고 허용 행동·선택 필드·금지 추론을 독립 작성한다. 불일치 건수와 항목을 기록한 뒤 합의한다. 합의되지 않은 사례는 실행 전에 명확히 고치고 재검토한다. 검토자·일시·사례 버전과 해시를 기록하되 실제 승인 전 이름·날짜를 채우지 않는다.
2. **개발·평가 분리:** NA-SEM-01~04와 기존 러너의 개발용 8건으로 실행 경로를 점검한다. 새 20건은 프롬프트 수정에 사용하지 않는다. 실행 후 오류를 보고 프롬프트를 고치면 해당 데이터는 개발 자료가 되므로 재도전에는 새 평가 자료가 필요하다.
3. **실행 준비 확인:** 모델·프롬프트·스키마 버전, 설정, 20건 입력, 사람 기준, 시간·호출 예산, 원출력 저장 경로를 동결한다. 기존 네 필드 출력 계약을 사용하며 모델 출력에 ID·관계·enum을 추가하지 않는다. 실제 모델 실행은 사례 검토와 명시적 실행 요청 후 수행한다.
4. **모델 출력과 검사:** 최초 응답·종료 사유·복구 응답·호출 수·시간·사용량·검사 결과를 분리 기록한다. 각 회차의 최초 입력당 실행은 1회이며 유리한 응답을 고르는 반복 샘플링을 하지 않는다.
5. **대조:** 합의된 사람 기준으로 최초 출력의 건별 성공·실패와 오류 유형을 판정한다. 사람끼리의 라벨 불일치와 모델 오류 건수는 별도로 집계한다. 구조 검사 통과를 의미 성공으로 세지 않는다.

평가용 20건과 합의한 사람 기준은 [evals/evalset.jsonl](../../evals/evalset.jsonl)에 공통으로 보관하고, 스파이크 판정과 강의 7 Evals 보고는 분리한다. 데이터는 id·category·query·expect·graders·note 형식을 사용하고, 두 보고에서 같은 데이터 버전·라벨 버전·실행 ID를 참조한다. 같은 실행 결과를 두 개의 독립 실험으로 세지 않는다. 현재 evalset.jsonl은 자리표시자이며 20건 작성과 사람 검토는 미완료다. 공유 데이터의 결과를 보고 프롬프트를 수정했다면 이후에는 개발·회귀 자료로 표시하고, 새로운 평가 근거에는 사용하지 않은 자료를 별도로 준비한다.

**현재 실행 도구의 제약:** scripts/check_next_action_parser.py는 프롬프트 예시에서 만든 개발용 8건을 다루며 호출 상한은 16회다. 새 평가 파일 20건을 읽는 기능과 위 실험 전체 관리 절차는 현재 구현돼 있지 않다. 따라서 기존 명령을 그대로 실행해 이 계획을 완료할 수 있다고 안내하지 않는다. 실행 전 별도 평가 러너 또는 기존 도구 확장과 예산 제어를 검토·구현해야 한다. 이 계획은 현재 러너의 호출 상한·보호 장치와 제품 코드를 변경하지 않는다.

## 5. 결과

**미실행.** 새 평가용 20건·사람 독립 라벨·합의·실제 모델 출력이 없어 수치를 기입하지 않는다. 현재 오프라인 48/48, 정책 골든 14건, 브라우저 후보 회귀 결과는 개발용 검사이며 이 실험의 결과가 아니다.

| 항목 | 현재 기록 |
|---|---|
| 평가 사례·사람 기대값 버전 | 미작성·미확정 |
| 검토자 2명·승인 일시 | 미기록 |
| 사람 라벨 불일치·합의 건수 | 미측정 |
| 모델·프롬프트·설정·회차 | 미확정 |
| 실제 평가·최초 성공 건수와 비율 | 미실행·미측정 |
| 중대 오류·기타 오류 유형별 건수 | 미측정 |
| 복구 성공·호출 수·시간·사용량 | 미측정 |

오류는 행동 누락·잘못된 행동 선택·다른 행동의 상태 귀속·없는 장애/기한 생성·부정/인용 오해·형식/통신 실패로 구분한다. 한 사례에 여러 오류가 있으면 중복 집계 여부를 표시하며 오류 합계를 실패 사례 수로 오해하지 않게 한다. 실제 사례별 예시와 산출물 링크는 실행 후에만 추가한다.

## 6. 판단과 재도전 조건

**현재 판단: 보류.** 실제 모델 추출을 채택했다고 주장하지 않으며 현재 브라우저 앱의 규칙 기반 예시·직접 입력·수정·취소·사용자 확인 흐름을 유지한다.

| 향후 결과 | 결정과 명세 반영 |
|---|---|
| 18/20 이상·중대 오류 0건·전수 판정 완료 | 실제 모델 연결을 검토할 기술 근거로 사용. 자동 확정은 도입하지 않으며 별도 구현·통합 검증 전까지 SPEC의 미구현 표시 유지 |
| 중대 오류 발생 또는 18/20 미만 | 현 추출 방식 채택 보류·방식 변경 검토. 직접 입력을 유지하고 오류 유형에 따라 프롬프트·검토 절차를 수정한 뒤 별도 회차로 재검증 |
| 자료·라벨·실행 도구 부족, 시간/예산 소진, 판정 미완료 | 판단 보류. 부족한 항목과 부분 결과를 그대로 기록 |

재도전은 오류 원인·변경한 프롬프트/절차·새 평가 자료·사람 기준·예산을 준비한 뒤 실행 전에 조건을 다시 확정한다. 기존 실패 사례는 개발 회귀 자료로 보존하고, 같은 파일의 이 절 아래에 회차별 결과를 추가한다. 스파이크 통과를 AC3 전체·사용자 효과·서버 제품 완성이나 강의 7 Evals 제출 완료로 대체하지 않는다.
